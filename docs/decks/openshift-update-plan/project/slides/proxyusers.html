Who gets the proxy, and who doesn't

Platform components: get it

  • Cluster Version Operator: update graph, signatures
  • CRI-O on every node: image pulls
  • Image registry operator; Insights, only if enabled
  • Operators installed through OLM: their own deployments, and only operators we put in the catalog

Application namespaces: don't

  • Application pods: no proxy variables injected
  • Pods an operator creates: only if that operator sets them
  • Proxy settings are per container: one pod's never reach another
  • A team that sets its own proxy does so deliberately, as policy allows today

Only two places a platform component touches other namespaces, both closed:

1 · CRI-O pulls every pod's image through the proxy: it carries images only, never app traffic, and only from repositories on allowedRegistries

2 · Operators: we control the catalog, so only ones we approved can be installed, and a Subscription can unset the proxy for one that does not need it

[R2] olm-overriding-proxy-settings.adoc: operators "must handle" proxy settings for the pods they manage · 11

The proxy is a platform setting: the Machine Config Operator writes it to the nodes for CRI-O and the kubelet, and platform operators read it for their own deployments. Nothing writes it into application pods. OLM's Subscription spec.config.env can also set HTTP_PROXY, HTTPS_PROXY and NO_PROXY to empty values for an operator that does not need the proxy; Red Hat documents that empty values unset them.
