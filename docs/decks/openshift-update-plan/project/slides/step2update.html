One update hop under the proxy

Nothing to prepare

No sync, nothing to mirror, no local Update Service. The hop needs only its change window, and the playbook runs it.

Red Hat does the rest

The cluster reads the graph, pulls the release by digest and checks the signature itself, through the proxy, as a connected cluster does.

Red boxes

An unhealthy cluster, a graph that does not arrive, a version not recommended, a signature not verified: the run stops.

This is the recurring workflow under the proxy option, the counterpart of the scheduled sync on the Step 3 slide. There is no timer because an update is a planned change window, not a sync: the update playbook starts the hop, the cluster's own update machinery does the work through the proxy, and the playbook waits, checks every operator and pool, and refuses to go on unless the CVO verified the release signature. The verify playbook then writes the evidence file for security. The hops from 4.18 through 4.19 to 4.20 and later 4.22 are each this same run. Compare with Step 3, where every hop first needs a mirroring run, the Update Service restarted and the cluster resources applied.
