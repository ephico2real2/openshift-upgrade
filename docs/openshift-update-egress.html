platform engineering · design decision · 2026-09-25 · checked against OpenShift 4.22

How our OpenShift clusters should reach Red Hat to stay current

Our clusters run disconnected, so every update starts with a manual mirror. Red Hat ships a z-stream for the newest minor about weekly (4.22.1 to 4.22.15 came out every 7 days, 16 Jun to 22 Sep 2026) and a new minor about every four months, and it expects customers on the latest 4.x.z. This page checks both proposed designs against Red Hat's documentation and product source, draws them, and adds a third design that the research supports.

What the research found

Each point is traced to a document or source file in the tables below.

  • Every design opens quay.io and registry.redhat.io at the firewall. They differ only in which machines use that opening: every cluster node (Option 1) or one mirror host (Options 2 and 3).
  • Neither option needs two-headed DNS. Behind an HTTP CONNECT proxy, nodes resolve only the proxy's name; the proxy resolves Red Hat's names. Quay's repository mirroring and oc-mirror both accept a proxy setting too.
  • The "Quay image sync" in Option 2 is not the documented way to mirror OpenShift content. The 4.22 docs name oc-mirror plugin v2. Quay repository mirroring copies tags by glob, one repository at a time, and has no logic for release payloads, operator catalogs, signatures or the update graph.
  • Enabling the cluster-wide proxy drains and reboots every node once. Updating the pull secret changes nothing on the nodes. Editing mirror sets drains the nodes and reloads CRI-O; the MCO code shows no reboot, although one paragraph of the docs says there is one.
  • Since 4.21, signature checks are on by default for release images. Any design that serves release images from a mirror must also mirror their sigstore signatures, or node updates stop.
  • Git by itself enforces nothing on operator catalogs. Default RBAC already stops namespace admins from adding catalogs. disableAllDefaultSources hides only Red Hat's defaults, and does not touch the OLM v1 catalogs. Only an admission policy also binds cluster-admins and Argo CD. A filtered catalog also needs a registry to host its image.

Option 1 · allowlist Red Hat URLs + cluster-wide proxy

a. No two-headed DNS required holds, with conditions With CONNECT, the client sends only the destination host and port to the proxy, and the proxy opens the connection (RFC 9110 §9.3.6). CRI-O, the CVO and the operators use Go's proxy transport, so nodes resolve only the proxy's name and noProxy names. Conditions: the authentication and console operators probe their *.apps routes through the proxy, and the apps domain is not added to noProxy automatically, so add .apps.<cluster>.<domain>. NTP (UDP 123) needs an internal source. b. Configure the OpenShift proxy holds, with conditions This is a documented configuration (proxy.config.openshift.io/cluster). Cost: "the Machine Config Operator (MCO) reboots all nodes in your cluster" when you enable it, and again when httpProxy, httpsProxy or noProxy change, because the MCO writes /etc/mco/proxy.env and that file is not on its list of files it changes without a reboot. A trustedCA-only change restarts CRI-O and does not reboot. Option 2 · internal Quay, two-headed DNS, sync, OSUS
a1. Two-headed DNS is needed so Quay can reach Red Hat does not hold Each Quay repository mirror has its own "HTTPS Proxy" and "No Proxy" settings, which Quay passes to skopeo. oc-mirror v2 "can operate in a proxy-configured environment" (GA in 4.18). a2. Its worker code has no logic for release image references, catalog relatedImages, signatures or the update graph. A 4.22.15 release references 191 component images by digest, and 4.22.*-x86_64 matches 58 tags on quay.io, of which only 17 are GA x86_64 releases; the other 41 are pre-release or multi-arch variants. Both options say "limit the catalog via Git". Git is where changes get reviewed, but it enforces nothing. The figure follows a Subscription through the gates that can refuse it, in the order the API server, OLM and CRI-O apply them.

Admission policy for model A: the CatalogSource rule 
# Tested on kind with the OLM CRDs on Kubernetes 1.31.14 (the OpenShift 4.18 base) and 1.37.0: 19/19 cases,
# including system:masters being denied. Not yet run on a live OpenShift cluster.
# Roll out with validationActions: [Warn, Audit] first, then switch to Deny.
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: restrict-olm-catalogsources
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: ["operators.coreos.com"]
      apiVersions: ["*"]
      operations: ["CREATE", "UPDATE"]
      resources: ["catalogsources"]
  variables:
  - name: approvedPrefixes            # trailing "/" stops look-alike hosts such as mirror.corp.example.com.evil.io
    expression: "['mirror.corp.example.com/olm/']"
  - name: annotations
    expression: "has(object.metadata.annotations) ? object.metadata.annotations : {}"
  validations:
  - expression: "request.namespace == 'openshift-marketplace'"
    message: "CatalogSource objects are only permitted in openshift-marketplace."
  - expression: "has(object.spec.sourceType) && object.spec.sourceType == 'grpc' && has(object.spec.image) && !has(object.spec.address)"
    message: "Only image-backed gRPC CatalogSources are permitted (no configmap or address sources)."
  - expression: "has(object.spec.image) && variables.approvedPrefixes.exists(p, object.spec.image.startsWith(p))"
    message: "spec.image must come from an approved catalog repository."
  - expression: "!('olm.catalogImageTemplate' in variables.annotations) || variables.approvedPrefixes.exists(p, variables.annotations['olm.catalogImageTemplate'].startsWith(p))"
    message: "olm.catalogImageTemplate must point at an approved catalog repository."

The full set also covers Subscriptions (approved catalogs only; Manual approval, with OLM's own service account exempt because OLM creates dependency Subscriptions as Automatic) and OLM v1 ClusterCatalogs. mirror.corp.example.com/olm/ is a placeholder.

Decisions

D1 · design
Which design do we build?
It depends on one security answer: which machines may reach Red Hat through the proxy. Option 1 uses only documented configuration and needs no mirror to run. Option 3 keeps our registry and limits the clusters to update metadata, but Red Hat has not documented that combination. Option 2 keeps clusters fully closed, but it means running oc-mirror, an HA Quay and OSUS.
Recommend Option 1 if security approves node egress to the four host groups with the controls above. If it approves only api.openshift.com and mirror.openshift.com from the clusters, use Option 3, and add a CI gate so the cluster is only told to go to versions already mirrored. With no cluster egress at all, use Option 2 in its documented form: oc-mirror v2, not Quay repository mirroring.
D2 · catalog model
Filtered catalog (model A) or an allowlist on the stock catalog (model B)?
Model A shows developers only what they may install, but it needs a registry for the catalog image. Model B needs no registry, but the full catalog stays visible in the console, and every dependency has to be listed by hand.
Recommend model A and keep our current registry for the catalog image alone. That leaves the admission policy one prefix to check.
D3 · telemetry
Keep telemetry and Insights on?
The firewall doc lists the telemetry hosts only "if you do not disable Telemetry". Updates do not use them. Turning telemetry off removes three hosts from the request, and we lose Insights recommendations.
Security team's call. Leaving it off makes the first approval smaller, and it can be turned on later without touching nodes.
D4 · TLS interception
Will the proxy decrypt traffic to Red Hat hosts?
Interception is the only way to filter quay.io by repository at the network layer. It needs the proxy CA in trustedCA. Red Hat's support position on it could not be verified.
Exempt the Red Hat hosts from interception until Support answers. The CVO checks GPG signatures and CRI-O checks sigstore signatures, so payload integrity does not depend on the proxy.
D5 · cadence
How often do we update?
Z-streams for the newest minor ship weekly. Full support lasts 6 months, or until 90 days after the next minor's GA, whichever is later; maintenance runs to 18 months. Even minors get EUS (4.22 EUS Term 1 runs to 2028-06-30). 4.18 left maintenance on 2026-08-25.
Recommend a monthly z-stream window from stable, and EUS-to-EUS minors for production. Control-plane-only updates work between even minors.
